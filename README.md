# Mail Agent — мини-ассистент для почты Outlook (тестовое задание)

Java 8 / Maven консольное приложение: читает непрочитанные письма из Outlook
(через JACOB/COM), передаёт их LLM с набором инструментов (tool-calling),
исполняет вызванные инструменты (напоминания, поиск по ним, текущая дата) и
отправляет ответ автору письма. Идемпотентно (не обрабатывает письмо повторно),
переживает рестарт, деградирует без падений при недоступности LLM или Outlook.

## Требования

- Java 8 (JDK, не JRE) — например Eclipse Temurin 8.
- Maven 3.6+ (в этом репозитории использовался локальный дистрибутив, см. ниже).
- Для реального (не `--mock`) запуска: Windows с установленным Microsoft Outlook
  (desktop, не веб-версия) и настроенным профилем.

Если Maven не установлен глобально, дистрибутив можно взять из
`assesment/other/tools/apache-maven-3.9.9/bin/mvn` (не входит в этот
git-репозиторий — рабочий инструмент, а не часть продукта).

## Сборка

```bash
mvn clean package
```

Собирает fat-jar со всеми зависимостями (`maven-shade-plugin`):
`target/mail-agent.jar`. Перед `package` автоматически прогоняются тесты
(`mvn test`), они должны быть зелёными без установленного Outlook/JACOB —
нативная зависимость `jacob` исключена из test-classpath через
`classpathDependencyExcludes` в конфигурации surefire (`pom.xml`).

## Тесты

```bash
mvn test
```

86/86 тестов, зелёные без Outlook и без `jacob`-DLL на PATH. Покрытие
детерминированной логики (JaCoCo, `target/site/jacoco/index.html` после
`mvn test`) по ключевым пакетам:

| `mail` (без `OutlookMailChannel`) | 94.4% |
| `llm` (без сетевой части `HttpLlmClient`) | 100% |
| `tools` | 97.2% |

| **Итого по целевым пакетам** | **96.0% (478/498)** |

`OutlookMailChannel` (0%) и `ru.assistant.App` (64.6%, composition root) —

через `MockMailChannel`); `App` — main-catch/бесконечный цикл поллинга и
реальная проводка Outlook/HTTP, уже проверены через `AppSmokeTest`
(`--mock --once`) и ручной прогон fat-jar (см. ниже).

## Запуск

Демо-режим без Outlook и без LLM-ключа (мок-канал почты со сценарным письмом
и мок-LLM с заранее заданным диалогом), одна итерация:

```bash
java -jar target/mail-agent.jar --mock --once
```

Реальный режим (на машине с установленным Outlook и настроенным LLM-ключом),
бесконечный поллинг:

```bash
set LLM_API_KEY=sk-...
java -jar target/mail-agent.jar
```

Флаги:

| Флаг | Назначение |
|---|---|
| `--mock` | `MockMailChannel` + `MockLlmClient` вместо реального Outlook/HTTP |
| `--once` | одна итерация обработки вместо бесконечного поллинга |
| `--config=<путь>` | явный путь к YAML-конфигу (по умолчанию — `config/config.local.yaml`, если существует, иначе `config/config.example.yaml`) |

## Конфигурация

Файл `config/config.example.yaml` — шаблон, безопасно коммитить (без
секретов). Для реального запуска скопировать в `config/config.local.yaml`
(игнорируется git, см. `.gitignore`) и подставить свои значения:

```yaml
llm:
  endpoint: "https://api.openai.com/v1/chat/completions"
  model: "gpt-4o-mini"
  apiKeyEnv: "LLM_API_KEY"   # имя переменной окружения, НЕ сам ключ
  timeoutMs: 15000

agent:
  maxSteps: 6                # предохранитель от бесконечного tool-calling цикла

store:
  path: "./data"             # каталог для seen.json / reminders.json / audit.jsonl

mail:
  pollSeconds: 30
  profile: "Outlook"
  folder: "Inbox"
```

Секрет (`LLM_API_KEY`) читается только из переменной окружения
(`EnvSecretResolver`) — никогда не хранится в конфиге или в git.

## Архитектура (кратко)

- `mail/` — абстракция почтового канала (`MailChannel`): `OutlookMailChannel`
  (JACOB/COM, продакшн) и `MockMailChannel` (тесты/демо).
- `llm/` — абстракция LLM (`LlmClient`): `HttpLlmClient` (OpenAI-совместимый
  chat-completions API через okhttp) и `MockLlmClient` (детерминированный,
  для тестов и `--mock`).
- `tools/` — инструменты, вызываемые моделью: `current_datetime`,
  `add_reminder`, `find_items` (+ `ReminderStore` — их персистентное
  хранилище на диске).
- `agent/` — `AgentToolLoop` (цикл tool-calling с ограничением `maxSteps`),
  `MailProcessingService` (идемпотентная оркестрация: fetch → mark-if-new →
  tool-loop → reply, с откатом отметки при сбое), `SeenStore` (id уже
  обработанных писем, переживает рестарт).
- `infra/` — `AtomicJsonFileStore` (атомарная запись JSON на диск,
  общий для `SeenStore`/`ReminderStore`), `AuditLog` (append-only JSONL
  журнал действий со связкой хэшей — обнаруживает повреждение задним числом),
  `LogEvents`/`Sha256` (PII-безопасные структурные логи).
- `App.java` — composition root: сборка графа зависимостей из конфига,
  разбор `--mock`/`--once`/`--config`.

Подробный план разработки с обоснованием решений — `PLAN.md` в этом каталоге.
Простое, непрограммистское описание того, как это работает — в
`assesment/other/архитектура-для-непрограммиста.md` (вне этого репозитория,
не входит в сдаваемый продукт).

## Идемпотентность и устойчивость к сбоям

- Каждое письмо отмечается как «увиденное» (`SeenStore`, файл `seen.json`)
  сразу после получения id, но **до** отправки ответа; если tool-loop или
  отправка ответа падают — отметка откатывается, чтобы письмо было
  обработано повторно на следующем цикле (не теряется, но и не считается
  успешно обработанным преждевременно).
- `SeenStore`/`ReminderStore` пишутся атомарно (temp-file + rename) —
  повреждение файла при падении процесса посреди записи исключено.
- Недоступность LLM (сетевая ошибка, таймаут, 5xx) — перехватывается,
  логируется как WARN с ключом события (без стектрейса пользователю),
  письмо не отмечается как окончательно обработанное, попытка повторяется
  на следующем цикле поллинга.
- Недоступность Outlook (COM-ошибка) — аналогично, конкретное письмо/цикл
  пропускается с WARN-логом, процесс не падает.

## Аудит и логи

`AuditLog` (`data/audit.jsonl`) — append-only журнал ключевых событий
(получено письмо, вызван инструмент, отправлен ответ, сбой) с hash-chain
(каждая запись содержит SHA-256 хэш предыдущей) — позволяет детектировать
факт и точку повреждения журнала задним числом. Логи (`logback`) и
`AuditLog` никогда не содержат полного тела/темы письма — только id письма,
ключи событий и usPreview-хэши (см. `LogEvents.safePreview`), что было
отдельно проверено в рамках security-review (`other/agent-logs/DECISIONS.md`).

## Известные отступления от буквы задания

- **JACOB 1.14.3 вместо заявленных 1.20/1.19.** На Maven Central под
  groupId `net.sf.jacob-project` реально резолвится только 1.14.3 —
  версии 1.19/1.20 на central не публиковались (проверено эмпирически через
  `mvn clean compile`, не только по документации на mvnrepository.com).
  Контракт `MailChannel`/`OutlookMailChannel` не зависит от точной версии
  JACOB — интерфейс `com.jacob.com.Dispatch`/`ActiveXComponent` стабилен.
- **`OutlookMailChannel` не проверялся с реальным Outlook** на машине
  разработки (нет тестового почтового ящика, нет живого профиля Outlook на
  этой машине). Написан по контракту `MailChannel` и документации JACOB,
  покрыт контрактными тестами через `MockMailChannel`. Требует ручной
  проверки на экзаменационной машине с установленным Outlook.
- **Финальный smoke-тест с реальным LLM-ключом не проводился** — по
  умолчанию везде используется `MockLlmClient` (детерминированный,
  бесплатный), чтобы не тратить деньги пользователя без явной необходимости.
  `HttpLlmClient` покрыт тестами через `MockWebServer` (реальный HTTP-стек,
  без реального внешнего эндпоинта).

## Как я работал с ИИ

Разработка велась через Claude Code (агентский режим) при активном участии
пользователя: сначала согласован `PLAN.md` (пофазовый план с TDD-циклами
red→green, точками коммита и session-break), затем каждая фаза реализована
строго по TDD — сначала падающий тест отдельным коммитом, затем реализация
зелёным коммитом (видно в `git log`). Экспорт полной сессии — в
`claude-session-export/` в этом каталоге.

Перед подключением каждой новой библиотеки агент сверялся с официальной
документацией (WebSearch/WebFetch), а не полагался на память модели —
например, формат tool-calling для OpenAI-совместимого API и параметры
`maven-shade-plugin`/`jacoco-maven-plugin` уточнялись по актуальной
документации перед реализацией T4.3/T9.2/T10.2.

Значимые решения, где агент отклонился от первоначального плана или задания,
и почему — задокументированы в `other/agent-logs/DECISIONS.md` (вне этого
репозитория). Например: аудит-журнал изначально рассматривался как HMAC, но
реализован как SHA-256 hash-chain — не требует хранения секретного ключа для
подписи, при этом даёт то же свойство «повреждение задним числом
обнаруживаемо», а расширение до HMAC возможно позже без изменения внешнего
контракта `AuditLog.append/verify`.
