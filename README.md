# Mail Agent — мини-ассистент для почты Outlook (тестовое задание)

Java 8 / Maven консольное приложение: читает непрочитанные письма из Outlook
(через JACOB/COM), передаёт их LLM с набором инструментов (tool-calling),
исполняет вызванные инструменты (напоминания, поиск по ним, текущая дата) и
отправляет ответ автору письма. Идемпотентно (не обрабатывает письмо повторно),
переживает рестарт, деградирует без падений при недоступности LLM или Outlook.

## Требования

- Java 8 (JDK, не JRE) — например Eclipse Temurin 8.
- Maven 3.6+ (в этом репозитории использовался локальный дистрибутив, см. ниже).
- Для реального (не `--mock`) запуска: Windows с установленным Microsoft Outlook
  (desktop, не веб-версия) и настроенным профилем.

Если Maven не установлен глобально, дистрибутив можно взять из
`assesment/other/tools/apache-maven-3.9.9/bin/mvn` (не входит в этот
git-репозиторий — рабочий инструмент, а не часть продукта).

## Сборка

```bash
mvn clean package
```

Собирает fat-jar со всеми зависимостями (`maven-shade-plugin`):
`target/mail-agent.jar`. Перед `package` автоматически прогоняются тесты
(`mvn test`), они должны быть зелёными без установленного Outlook/JACOB —
нативная зависимость `jacob` исключена из test-classpath через
`classpathDependencyExcludes` в конфигурации surefire (`pom.xml`).

## Тесты

```bash
mvn test
```

86/86 тестов, зелёные без Outlook и без `jacob`-DLL на PATH. Покрытие
детерминированной логики (JaCoCo, `target/site/jacoco/index.html` после
`mvn test`) по ключевым пакетам:

| Пакет | Покрытие строк |
|---|---|
| `config` | 97.6% |
| `mail` (без `OutlookMailChannel`) | 94.4% |
| `llm` (без сетевой части `HttpLlmClient`) | 100% |
| `tools` | 97.2% |
| `agent` | 99.0% |
| `infra` | 89.0% |
| **Итого по целевым пакетам** | **96.0% (478/498)** |

`OutlookMailChannel` (0%) и `ru.assistant.App` (64.6%, composition root) —
осознанно вне целевого списка: `OutlookMailChannel` требует реального Outlook
+ нативного JACOB (недоступны на машине разработки, покрывается контрактно
через `MockMailChannel`); `App` — main-catch/бесконечный цикл поллинга и
реальная проводка Outlook/HTTP, уже проверены через `AppSmokeTest`
(`--mock --once`) и ручной прогон fat-jar (см. ниже).

## Запуск

Демо-режим без Outlook и без LLM-ключа (мок-канал почты со сценарным письмом
и мок-LLM с заранее заданным диалогом), одна итерация:

```bash
java -jar target/mail-agent.jar --mock --once
```

Реальный режим (на машине с установленным Outlook и настроенным LLM-ключом),
бесконечный поллинг:

```bash
set LLM_API_KEY=sk-...
java -jar target/mail-agent.jar
```

Флаги:

| Флаг | Назначение |
|---|---|
| `--mock` | `MockMailChannel` + `MockLlmClient` вместо реального Outlook/HTTP |
| `--once` | одна итерация обработки вместо бесконечного поллинга |
| `--config=<путь>` | явный путь к YAML-конфигу (по умолчанию — `config/config.local.yaml`, если существует, иначе `config/config.example.yaml`) |

## Конфигурация

Файл `config/config.example.yaml` — шаблон, безопасно коммитить (без
секретов). Для реального запуска скопировать в `config/config.local.yaml`
(игнорируется git, см. `.gitignore`) и подставить свои значения:

```yaml
llm:
  endpoint: "https://api.openai.com/v1/chat/completions"
  model: "gpt-4o-mini"
  apiKeyEnv: "LLM_API_KEY"   # имя переменной окружения, НЕ сам ключ
  timeoutMs: 15000

agent:
  maxSteps: 6                # предохранитель от бесконечного tool-calling цикла

store:
  path: "./data"             # каталог для seen.json / reminders.json / audit.jsonl

mail:
  pollSeconds: 30
  profile: "Outlook"
  folder: "Inbox"
```

Секрет (`LLM_API_KEY`) читается только из переменной окружения
(`EnvSecretResolver`) — никогда не хранится в конфиге или в git.

## Архитектура (кратко)

- `mail/` — абстракция почтового канала (`MailChannel`): `OutlookMailChannel`
  (JACOB/COM, продакшн) и `MockMailChannel` (тесты/демо).
- `llm/` — абстракция LLM (`LlmClient`): `HttpLlmClient` (OpenAI-совместимый
  chat-completions API через okhttp) и `MockLlmClient` (детерминированный,
  для тестов и `--mock`).
- `tools/` — инструменты, вызываемые моделью: `current_datetime`,
  `add_reminder`, `find_items` (+ `ReminderStore` — их персистентное
  хранилище на диске).
- `agent/` — `AgentToolLoop` (цикл tool-calling с ограничением `maxSteps`),
  `MailProcessingService` (идемпотентная оркестрация: fetch → mark-if-new →
  tool-loop → reply, с откатом отметки при сбое), `SeenStore` (id уже
  обработанных писем, переживает рестарт).
- `infra/` — `AtomicJsonFileStore` (атомарная запись JSON на диск,
  общий для `SeenStore`/`ReminderStore`), `AuditLog` (append-only JSONL
  журнал действий со связкой хэшей — обнаруживает повреждение задним числом),
  `LogEvents`/`Sha256` (PII-безопасные структурные логи).
- `App.java` — composition root: сборка графа зависимостей из конфига,
  разбор `--mock`/`--once`/`--config`.

Подробнее об архитектуре и структуре кода — [ARCHITECTURE.md](ARCHITECTURE.md).
Подробный план разработки с обоснованием решений — [PLAN.md](PLAN.md) в этом
каталоге. Простое, непрограммистское описание того, как это работает — в
`assesment/other/архитектура-для-непрограммиста.md` (вне этого репозитория,
не входит в сдаваемый продукт).

## Идемпотентность и устойчивость к сбоям

- Каждое письмо отмечается как «увиденное» (`SeenStore`, файл `seen.json`)
  сразу после получения id, но **до** отправки ответа; если tool-loop или
  отправка ответа падают — отметка откатывается, чтобы письмо было
  обработано повторно на следующем цикле (не теряется, но и не считается
  успешно обработанным преждевременно).
- `SeenStore`/`ReminderStore` пишутся атомарно (temp-file + rename) —
  повреждение файла при падении процесса посреди записи исключено.
- Недоступность LLM (сетевая ошибка, таймаут, 5xx) — перехватывается,
  логируется как WARN с ключом события (без стектрейса пользователю),
  письмо не отмечается как окончательно обработанное, попытка повторяется
  на следующем цикле поллинга.
- Недоступность Outlook (COM-ошибка) — аналогично, конкретное письмо/цикл
  пропускается с WARN-логом, процесс не падает.

## Аудит и логи

`AuditLog` (`data/audit.jsonl`) — append-only журнал ключевых событий
(получено письмо, вызван инструмент, отправлен ответ, сбой) с hash-chain
(каждая запись содержит SHA-256 хэш предыдущей) — позволяет детектировать
факт и точку повреждения журнала задним числом. Логи (`logback`) и
`AuditLog` никогда не содержат полного тела/темы письма — только id письма,
ключи событий и usPreview-хэши (см. `LogEvents.safePreview`), что было
отдельно проверено в рамках security-review (`other/agent-logs/DECISIONS.md`).

## Известные отступления от буквы задания

- **JACOB 1.14.3 вместо заявленных 1.20/1.19.** На Maven Central под
  groupId `net.sf.jacob-project` реально резолвится только 1.14.3 —
  версии 1.19/1.20 на central не публиковались (проверено эмпирически через
  `mvn clean compile`, не только по документации на mvnrepository.com).
  Контракт `MailChannel`/`OutlookMailChannel` не зависит от точной версии
  JACOB — интерфейс `com.jacob.com.Dispatch`/`ActiveXComponent` стабилен.
- **`OutlookMailChannel` не проверялся с реальным Outlook** на машине
  разработки (нет тестового почтового ящика, нет живого профиля Outlook на
  этой машине). Написан по контракту `MailChannel` и документации JACOB,
  покрыт контрактными тестами через `MockMailChannel`. Требует ручной
  проверки на экзаменационной машине с установленным Outlook.
- **Финальный smoke-тест с реальным LLM-ключом не проводился** — по
  умолчанию везде используется `MockLlmClient` (детерминированный,
  бесплатный), чтобы не тратить деньги пользователя без явной необходимости.
  `HttpLlmClient` покрыт тестами через `MockWebServer` (реальный HTTP-стек,
  без реального внешнего эндпоинта).

## Как я работал с ИИ

Разработка велась через Claude Code (агентский режим, VSCode-расширение) при
активном участии пользователя. Полный экспорт сессии (все промпты, планы,
tool-calls, включая субагентов) — в
[claude-session-export/](claude-session-export/) в этом каталоге.

### Стратегия промптов и планирования

- **Plan-first, с согласованием до кода.** Сначала пользователь и агент вместе
  сформулировали правила работы (`CLAUDE.md`, `.claude/settings.json` —
  рабочей области целиком, вне этого репозитория) — границы прав на
  чтение/запись/скачивание, требование TDD, требование сверяться с
  документацией, — и только после этого агент получил разрешение писать
  [PLAN.md](PLAN.md). Сам [PLAN.md](PLAN.md) (план по фазам, ~40 КБ) тоже
  был утверждён пользователем до первой строчки кода.
- **Декомпозиция с явной разметкой трудозатрат и параллелизма.** Каждая задача
  в [PLAN.md](PLAN.md) помечена уровнем усилия (Effort: L/M/H — механическая
  работа vs архитектурное решение, требующее внимания в основной сессии, а не
  в субагенте) и группой параллельности (`[∥ group=A]` — например,
  `MailChannel`, `LlmClient`, инструменты и PII-маскирование не зависят друг
  от друга и после готовности `Msg`/`AppConfig` делались независимыми
  ветками).
- **Точки коммита и session-break прописаны заранее.** В [PLAN.md](PLAN.md)
  для каждой фазы указан commit point (`CP-N`, перед которым `mvn test`
  обязан быть зелёным) и рекомендованная точка `git push`, а также две точки
  `SESSION BREAK` — заранее выбранные места для начала новой сессии Claude
  Code (ориентир ~300k токенов на сессию, см. `DECISIONS.md` — рабочий
  журнал решений вне этого репозитория), чтобы не терять качество из-за
  компрессии длинного контекста.
- **Журналы вместо длинной памяти диалога.** Прогресс велся в трёх файлах
  `other/agent-logs/` (вне этого репозитория — рабочие артефакты, не часть
  сдаваемого продукта) с разным назначением: `STATE.md` (перезаписываемый
  снимок «где мы сейчас», читается первым при возобновлении), `PROGRESS.md`
  (чек-лист фаз [PLAN.md](PLAN.md)) и `DECISIONS.md` (append-only журнал
  решений и отклонений с обоснованием) — это позволяло продолжать работу
  после прерывания или новой сессии, читая несколько КБ вместо всей истории.
- **TDD буквально, а не по названию.** Для каждого модуля — сначала падающий
  тест отдельным коммитом (`T*.* RED`), потом реализация отдельным коммитом
  (`T*.* GREEN`); переход red→green виден в `git log` как минимум двумя
  коммитами на функциональную единицу.
- **Субагенты — для изолированных и параллельных подзадач**, а не по
  умолчанию: например, `other/архитектура-для-непрограммиста.md` (T11.2)
  делегирован субагенту `general-purpose`, пока основная сессия занималась
  Phase 8–10; результат был проверен и принят без правок.

### Что проверяли у модели (не полагались на память)

- **Версия JACOB.** Задание указывало `net.sf.jacob-project:jacob:1.20`/1.19.
  При добавлении зависимости (T0.1) `mvn clean compile` показал, что на
  Maven Central резолвится только `1.14.3` — версии 1.19/1.20 там не
  публиковались (фигурируют только на сторонних агрегаторах вроде
  mvnrepository.com, но не в `repo.maven.apache.org`). Проверено эмпирически,
  не только по документации — итоговая версия `1.14.3` зафиксирована в
  `pom.xml`.
- **Формат tool-calling и сторонние библиотеки.** Перед реализацией
  `HttpLlmClient` (T4.3) — WebFetch документации okhttp
  (`OkHttpClient.Builder`, таймауты) и формата tool-calling OpenAI-совместимого
  chat-completions API; перед `maven-shade-plugin` (T9.2) и
  `jacoco-maven-plugin` (T10.2) — актуальные параметры конфигурации по
  официальной документации, а не по общим знаниям модели о более старых
  версиях.
- **Причина падения теста — не всегда баг в коде.** `HttpLlmClientTest`
  (okhttp `MockWebServer` на `127.0.0.1`) дважды падал с
  `BindException: Cannot assign requested address`. Вместо правки кода —
  воспроизведение голым `java.net.Socket`/`ServerSocket` и `git stash` на
  чистом коммите показали, что причина — AmneziaVPN на машине разработки,
  ломающий loopback TCP; после отключения VPN тест стабильно зелёный
  (задокументировано в `DECISIONS.md` как заметка на будущее).

### Что отклонили или скорректировали

- **HMAC → SHA-256 hash-chain для `AuditLog`.** Задание ссылается на
  референсный `HmacSigner` из внутреннего проекта заказчика («Коля»),
  исходников которого на этой машине нет. Вместо HMAC (требует хранения и
  защиты секретного ключа подписи) выбран hash-chain: каждая запись содержит
  SHA-256 предыдущей — даёт то же свойство «повреждение задним числом
  обнаруживаемо» без секрета, с возможностью позже добавить HMAC без смены
  внешнего контракта `AuditLog.append/verify`.
- **Реальный Outlook/JACOB — не устанавливаем.** По условиям задания
  ожидалась Windows-машина с готовым тестовым ящиком, примерами писем и
  предустановленной `jacob-1.20.x64.dll`. На машине разработки этого нет
  (личный компьютер, без тестового ящика и примеров писем) — решение
  пользователя: `OutlookMailChannel` пишется по контракту `MailChannel` и
  документации JACOB, проверяется только через `MockMailChannel`; живой
  прогон — задача экзаменационной среды.
- **Реальный LLM-ключ — не расходуем без явной просьбы.** Везде по умолчанию
  (разработка и все юнит-тесты) — `MockLlmClient`, детерминированный и
  бесплатный; `HttpLlmClient` проверен реальным HTTP-стеком через
  `MockWebServer`, но не живым внешним эндпоинтом — чтобы не тратить деньги
  пользователя без прямого запроса на конкретный прогон.
- **Самостоятельное расширение своих же прав агентом — отклонено без явного
  подтверждения.** Черновик `.claude/settings.json` (разрешения для самого
  агента) не создавался автоматически даже после общего согласия
  пользователя на работу — потребовался отдельный структурированный вопрос
  пользователю («создать файл самому?»), прежде чем это было сделано;
  зафиксировано в `DECISIONS.md` как пример осторожности при
  self-modification действиях.
- **Дополнительные тесты после JaCoCo-отчёта — признаны не нужны.** Итоговое
  покрытие целевых пакетов (96.0%, T10.2) уже существенно выше ориентира
  ~80%+ из `CLAUDE.md`; непокрытые строки — это либо недостижимые в норме
  ветки (`IOException`/`NoSuchAlgorithmException` обёртки), либо код, уже
  проверенный иначе (`OutlookMailChannel` — контрактно через
  `MockMailChannel`, `App.main`/поллинг-цикл — через `AppSmokeTest` и ручной
  запуск fat-jar) — решено не писать тесты ради процента, а не ради риска.

Полный журнал решений с обоснованиями — `other/agent-logs/DECISIONS.md` (вне
этого репозитория, рабочий артефакт для нас, а не для продукта).
