# Архитектура mail-agent — для программиста не из этого домена

Ты — опытный разработчик (SAP ABAP), но конкретно с этим стеком (Java-агенты,
LLM tool-calling, COM-автоматизация Outlook) дела не имел. Этот документ — не
для «объяснить, что такое цикл» или «что такое интерфейс», а для того, чтобы
быстро замкнуть незнакомые именно *доменные* концепции на то, что тебе уже
знакомо из ABAP/SAP-мира, а потом пройтись по реальной структуре кода.

## 1. Что это вообще такое, в двух словах

Консольный Java-процесс, который в бесконечном цикле (или один раз, флаг
`--once`) опрашивает почтовый ящик Outlook, для каждого нового непрочитанного
письма отдаёт текст письма языковой модели (LLM) вместе со списком «функций»,
которые модель может попросить выполнить, исполняет то, что модель попросила
(0 или несколько раз подряд), и отправляет автору письма финальный текстовый
ответ, который модель сформулировала. Больше почти ничего не происходит —
никакого веб-сервера, никакой очереди сообщений, никакой БД. Единица работы —
одно письмо; параллелизма между письмами внутри одного цикла нет (простой
`for`).

## 2. Незнакомые концепции — привязка к тому, что ты уже знаешь

### 2.1 LLM tool-calling (aka «function calling»)

Это НЕ похоже на вызов RFC/BAPI напрямую тобой из кода. Это похоже на
ситуацию, когда ты отдаёшь пользователю (тут — языковой модели) *каталог
доступных BAPI* (имя + описание + сигнатура параметров в виде JSON Schema —
[ToolSpec.java](src/main/java/ru/assistant/llm/ToolSpec.java)), а дальше
пользователь сам решает, какой из них и с какими параметрами вызвать,
основываясь на тексте письма. Твой код не решает «что делать» — он просто:
1. Отдаёт модели весь диалог + каталог функций (`LlmClient.chat(messages, tools)`).
2. Модель либо возвращает готовый текст ответа, либо список «я хочу вызвать
   вот эту функцию с вот такими аргументами» (`ToolCall`).
3. Ты реально выполняешь названную функцию на своей стороне (модель ничего
   сама не исполняет — только просит), результат текстом кладёшь обратно в
   диалог как ещё одно сообщение (`ChatMessage.tool(...)`), и снова спрашиваешь
   модель — по кругу, пока она не перестанет просить вызовы или не кончится
   лимит шагов (`maxSteps`).

Ближайшая ABAP-аналогия — динамический вызов через `CALL FUNCTION
(dynamic_name)` с параметрами, которые тебе не ты сам выбрал, а получил от
внешней стороны, плюс ты обязан считать эту сторону «недоверенной» (см. §2.3
про идемпотентность и §6 про security-review). Реализация цикла —
[AgentToolLoop.java](src/main/java/ru/assistant/agent/AgentToolLoop.java).

Здесь используется де-факто отраслевой стандарт — формат OpenAI
`chat/completions` с полями `tools`/`tool_calls` (см. `HttpLlmClient`), это не
изобретение проекта.

### 2.2 JACOB / COM-автоматизация Outlook

`OutlookMailChannel` не общается с Outlook через какой-то нормальный сетевой
API (нет ни REST, ни RFC, ни очереди). Outlook desktop на Windows выставляет
себя как COM-объект (`Outlook.Application`), и JACOB — это JNI-мост,
позволяющий из Java дёргать этот COM-объект так, как это делал бы VBA-макрос
внутри самого Outlook. Практически это ближе всего к «GUI-скриптингу» или к
интеграции через нестандартный, нетипизированный, версионно-хрупкий канал —
никакой компилятор не проверит, что метод `"Reply"` действительно существует
у Dispatch-объекта, ты узнаешь об этом только в рантайме через
`ComFailException`. По духу это похоже на call transaction/BDC в SAP —
работает, но хрупко, привязано к конкретной версии UI/API и требует, чтобы
процесс физически имел доступ к живому Outlook (тут — установленный desktop
Outlook с настроенным профилем, никакого web/OWA).

Важно: этот код **не тестируется юнитами** (нет Outlook на машине разработки)
и не тестировался вживую — контракт `MailChannel` проверен через
`MockMailChannel`. Верификация «руками» — задача экзаменационной машины.

### 2.3 Идемпотентность / «seen»-стор

Проблема ровно та же, что «не обработать один и тот же IDoc/сообщение дважды»
в интеграционных сценариях SAP (`WE05`/tRFC-таблицы дедупликации). Здесь
решение простое и явное:
[SeenStore.java](src/main/java/ru/assistant/agent/SeenStore.java) —
`Set<String>` идентификаторов уже обработанных писем (`Msg.id` = Outlook
`EntryID`), персистентно сохранённый на диск JSON-файлом. Ключевой паттерн,
реализованный в
[MailProcessingService.java](src/main/java/ru/assistant/agent/MailProcessingService.java):

```
markIfNew(id) == false → пропустить письмо (уже видели)
markIfNew(id) == true  → отметили ДО обработки
    ...обработка (tool-loop, отправка ответа)...
    если что-то упало → unmark(id)   // компенсация, откат отметки
```

То есть отметка ставится оптимистично *до* фактического успеха, а откатывается
назад при сбое — классический pattern «mark-then-compensate», а не
«commit-after-success». Мотивация: если бы отметка ставилась только после
успеха, то параллельный/повторный `fetchUnread()` мог бы взять то же письмо в
обработку дважды, пока первая обработка ещё идёт. А если бы отметка не
откатывалась при сбое — временный сбой LLM/Outlook навсегда бы «похоронил»
письмо как «обработанное», хотя ответ так и не ушёл.

### 2.4 Аудит-журнал как hash-chain (не HMAC)

Это НЕ система подписи с секретным ключом (HMAC), а SHA-256 hash-chain — как
упрощённая идея из блокчейна: каждая запись хранит хэш предыдущей записи
(`prevHash`) и свой собственный хэш, вычисленный от `(seq, eventKey,
detailsJson, prevHash)`. `verify()` проходит по всей цепочке и, если кто-то
подменил задним числом хоть один символ в любой строке файла, хэши
«разъезжаются» начиная с этой записи — обнаруживается сам факт и номер
повреждённой записи. Отличие от HMAC — не нужен отдельный секретный ключ
(значит нет проблемы «где его хранить»), но и подделать заново всю цепочку
после места повреждения технически может кто угодно с доступом к файлу — это
detection tampering, а не cryptographic non-repudiation. Осознанное отступление
от референсного проекта задания (там HMAC) — подробное обоснование ведётся в
отдельном журнале решений вне этого репозитория. Реализация —
[AuditLog.java](src/main/java/ru/assistant/infra/AuditLog.java).

## 3. Структура пакетов и кто за что отвечает

```
ru.assistant
├── App.java              — composition root (см. §5)
├── config/                — YAML-конфиг → POJO, резолвинг секрета из env
│   ├── AppConfig, ConfigLoader, EnvSecretResolver
├── mail/                  — абстракция почтового канала
│   ├── MailChannel (interface): fetchUnread() / reply()
│   ├── OutlookMailChannel     — прод, JACOB/COM (см. §2.2)
│   ├── MockMailChannel        — тесты/демо, in-memory
│   └── Msg                    — POJO письма (id/from/subject/body/receivedAt)
├── llm/                   — абстракция LLM
│   ├── LlmClient (interface): chat(messages, tools) -> ChatResponse
│   ├── HttpLlmClient   — OpenAI-совместимый HTTP (okhttp), с ретраем на 5xx
│   ├── MockLlmClient   — очередь заранее заданных ChatResponse (для тестов)
│   └── ChatMessage / ToolSpec / ToolCall / ChatResponse — DTO диалога
├── tools/                 — «функции», которые модель может вызвать
│   ├── Tool (interface): name()/description()/jsonSchema()/execute(args)
│   ├── CurrentDatetimeTool, AddReminderTool, FindItemsTool
│   ├── ReminderStore   — персистентное хранилище напоминаний (JSON-файл)
│   └── ToolRegistry    — Map<name, Tool>, генерирует List<ToolSpec> для LlmClient
├── agent/                 — оркестрация
│   ├── AgentToolLoop         — цикл «спросить модель → выполнить её запросы» (§2.1)
│   ├── MailProcessingService — один цикл обработки почты (§2.3)
│   └── SeenStore              — идемпотентность (§2.3)
└── infra/                 — сквозные утилиты
    ├── AtomicJsonFileStore — temp-file + atomic rename, общий для Seen/ReminderStore
    ├── AuditLog            — hash-chain журнал событий (§2.4)
    ├── LogEvents           — константы ключей событий + PII-safe превью для логов
    └── Sha256              — обёртка MessageDigest
```

Все внешние по природе вещи (почта, LLM) — за интерфейсом с ровно двумя
реализациями: боевая и мок. Это стандартный «hexagonal»/ports-and-adapters
подход — если тебе ближе ABAP-терминология, это как БАПИ-обёртка с
возможностью подменить бэкенд-вызов заглушкой в тестовом клиенте.

## 4. Путь одного письма по коду (без метафор)

Точка входа — `MailProcessingService.processCycle()`:

1. `mailChannel.fetchUnread()` → `List<Msg>`. Если бросает
   `MailChannelException` — WARN-лог, событие `mail_channel_error`, выходим из
   `processCycle()` целиком (весь цикл поллинга пропущен, не отдельное письмо
   — на этом уровне ещё нет списка писем, чтобы обрабатывать по одному).
2. Для каждого `Msg` в списке:
   - `seenStore.markIfNew(msg.getId())` — если `false`, `continue` (уже
     обработано раньше, пропускаем без событий).
   - Если `true` — пишем аудит-событие `agent_mail_seen`, затем
     `toolLoop.run(msg.getBody())`:
     - Внутри `AgentToolLoop.run()`: собираем `List<ChatMessage>`, начиная с
       `ChatMessage.user(body)`. В цикле до `maxSteps` раз:
       `llmClient.chat(messages, toolRegistry.toToolSpecs())`.
       Если `response.getToolCalls()` пуст — это финальный ответ, возвращаем
       `response.getContent()` и выходим из цикла.
       Иначе — на каждый `ToolCall`: аудит-событие `agent_tool_call` (аргументы
       не пишутся в открытом виде — `LogEvents.safePreview` — длина + первые
       12 hex символов SHA-256), `toolRegistry.get(name)` → если инструмент не
       найден или JSON аргументов не парсится — не exception наружу, а
       текстовая строка `"Error: ..."` возвращается **самой модели** как
       результат вызова (модель может исправиться на следующем шаге). Если
       инструмент есть и аргументы распарсились — `tool.execute(args)`;
       `ToolError` из инструмента так же превращается в текст `"Error: ..."`
       для модели, а не течёт наружу как исключение.
     - Если ни разу не вышли досрочно за `maxSteps` итераций — событие
       `agent_maxsteps_exceeded`, возвращается фиксированный fallback-текст.
   - Если `toolLoop.run()` бросил `LlmException` (сеть недоступна, таймаут,
     5xx после ретрая, ошибка парсинга ответа) — `seenStore.unmark(id)`
     (откат!), WARN `llm_failed`, `continue` к следующему письму. **Reply не
     отправляется** — намеренно, чтобы не плодить автоответы при полном отказе
     LLM.
   - Если `toolLoop.run()` вернул текст — `mailChannel.reply(msg, reply)`.
     Если это бросает `MailChannelException` — тоже `unmark(id)`, WARN
     `mail_channel_error` со `stage=reply`, `continue`.
   - Если всё прошло — событие `agent_reply_sent`.

Обрати внимание: `try/catch` — на каждое письмо внутри цикла `for`, не один
обёрточный `try` на весь `processCycle()`. Значит один упавший email не
блокирует обработку остальных писем в том же цикле — это явное архитектурное
решение, не побочный эффект.

## 5. Composition root — `App.java`

Никакого DI-фреймворка (Spring и т.п.) — всё собирается руками в
`App.run(args)`: парсинг `--mock`/`--once`/`--config=`, загрузка YAML
(`ConfigLoader.load`), создание сторов (`ReminderStore`, `SeenStore`,
`AuditLog`) на путях из конфига, выбор реализации `MailChannel`/`LlmClient` в
зависимости от `--mock`, сборка `ToolRegistry` с тремя инструментами,
`AgentToolLoop`, `MailProcessingService`. Дальше либо один
`service.processCycle()` (`--once`), либо `while(true) { processCycle();
Thread.sleep(pollSeconds*1000) }`.

`--mock` подменяет и почту, и LLM на детерминированные in-memory реализации со
сценарным письмом «Какое сегодня число?» и заранее прописанным диалогом с
моделью (`tool_call current_datetime` → финальный текст) — специально чтобы
fat-jar можно было реально запустить и увидеть весь цикл целиком без Outlook и
без ключа LLM (см. [USE_GUIDE.md](USE_GUIDE.md)).

## 6. Тестовая стратегия

- Все внешние системы (Outlook, HTTP LLM-эндпоинт) закрыты интерфейсом с
  мок-реализацией — юнит-тесты никогда не трогают ни реальный Outlook, ни
  реальную сеть (кроме `HttpLlmClientTest`, который гоняет реальный HTTP-стек
  против `okhttp3:mockwebserver`, поднятого на loopback, — тоже не «настоящий»
  внешний сервис).
- `net.sf.jacob-project:jacob` (нативная COM-зависимость) исключён из
  test-classpath (`classpathDependencyExcludes` в surefire) — `mvn test`
  зелёный без установленного Outlook/JACOB DLL вообще где угодно.
- TDD red→green по каждому модулю — в git-истории видно отдельными коммитами.
- Golden-сценарии (`GoldenScenariosTest`) — 4 теста прямо на кейсы из задания:
  добавить напоминание / найти записи / спросить дату / пустое-мусорное письмо
  без побочных эффектов.
